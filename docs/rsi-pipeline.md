# Laya × RSI：推理 Pipeline 与受约束自进化方案

> 目标：把 Laya 放在 JEV 的 Decision Infra 层，先以“经验记忆 + 候选检索”实现可验证、可回滚的自进化；在离线证据充分后，再进入检索器或决策头的模型级迭代。

## 1. 一句话定义

这里的 RSI（Recursive Self-Improvement）不是让模型无约束地重写自己，也不是让它用自己的预测反复训练自己。它是一套工程闭环：系统从**真实、可追溯的反馈**中提取经验，形成候选版本；候选版本必须经过独立评测、风险门禁和灰度验证，才可以替换线上版本；任一步不通过都能回滚。

Laya 在这个方案中不承担长文本生成，而是承担“在少量明确候选项中快速做 choice 或 score”的决策职责。JEV 的状态、工具、规则、风险等级和业务执行器仍是外部、可审计的系统能力。

## 2. 全局架构：在线决策与离线 RSI 如何闭环

<whiteboard type="blank"></whiteboard>

### 2.1 在线链路的职责

在线链路的目标是快速、稳定地从可控候选中得出决策。它不直接训练模型，也不直接修改经验库。

| 阶段 | 做什么 | 关键输入 | 关键输出 | 失败时怎么处理 |
|---|---|---|---|---|
| 输入规范化 | 清洗、脱敏、补齐 schema 与上下文 | JEV state、用户请求、权限 | 结构化决策请求 | 缺字段、越权或超范围则拒绝/澄清 |
| Embedding | 将请求压缩为语义向量 | 规范化请求 | query vector | 向量服务异常时走保守 fallback |
| Prototype retrieval | 从所有意图/动作里召回少量候选 | query vector、原型记忆版本 | Top-K 候选 | 召回不充分则扩大 K 或 abstain |
| Laya choice | 在候选内完成判别 | 请求、候选定义、判定准则 | choice、score、置信信号 | 结果不稳定时不自动执行 |
| 风险门禁 | 将“模型判断”转为“可执行决策” | choice、规则、风险等级 | execute / abstain / 人审 | 高风险场景默认不放行 |
| 反馈记录 | 记录全过程，支持离线归因 | 请求、候选、预测、执行结果 | 可追溯 event | 写入失败需告警，不能静默丢失 |

### 2.2 JEV 与 Laya 的边界

JEV 负责候选产生、权限、工具执行、状态一致性、观测与回滚；Laya 负责在候选集合中判别“最匹配的是谁”。这条边界很重要：即使 Laya 发生误判，也不应自动获得更大的动作权限。

## 3. 第一阶段 RSI：原型记忆自进化

<whiteboard type="blank"></whiteboard>

### 3.1 为什么先改记忆，不先改权重

原型记忆是每个类别的一组已验证经验样本及其向量表示。请求先和这些原型做语义匹配，只把最可能的 Top-K 类交给 Laya。相比直接微调权重，它有四个优势：

- 更新快：新增一条已确认案例即可产生新版本，不需要训练作业。
- 可解释：每个类别为什么被召回，能追溯到哪几条经验。
- 可回滚：memory version 直接切回上一版即可。
- 风险低：不改变 Laya 的基础能力，只改善“把哪些候选递给它”。

### 3.2 一轮自进化的输入、处理与输出

| 环节 | 输入 | 处理规则 | 输出 |
|---|---|---|---|
| 收集反馈 | 人工复核、规则校验、可验证执行结果 | 必须带真实标签或明确成功/失败证据 | 标注经验候选 |
| 数据过滤 | 标注经验候选 | 去重、脱敏、剔除冲突标签与低质量样本 | 合格 replay buffer |
| 分类别配额 | 合格 replay buffer | 每类每轮只提升有限条错误案例，防止高频类别淹没其他类别 | 有界增量样本 |
| 原型重算 | 当前 memory + 增量样本 | 对每类样本 embedding 做归一化聚合 | candidate memory version |
| 离线评测 | candidate version、冻结验证集 | 对比候选召回、准确率、延迟、关键类回归 | 指标报告 |
| 发布决策 | 指标报告、风险门禁 | 达标才进入 shadow/canary；否则保持旧版本 | publish 或 rollback |

### 3.3 绝不能跨越的四条线

1. 测试集不能用来挑经验、挑阈值、挑 Top-K 或决定是否继续更新；它只用于最终观察泛化效果。
2. 模型自己的预测不是标签。没有人工或外部可验证信号时，不能把预测写回 replay buffer。
3. 线上样本不能未经脱敏和权限审计直接进入训练或经验库。
4. 通过离线评测不等于自动上线；仍需 shadow、canary、回滚预案和线上漂移监控。

## 4. 实验基线：Banking77 证明了什么

本地实验选用 Banking77：77 个公开银行业务意图，适合模拟“候选很多、语义相近”的路由决策。该场景恰好测试 Laya 在大候选集下的短板与“先检索再 choice”的收益。

| 设定 | 数值 |
|---|---:|
| 初始 memory | 每类 1 条可信样本，共 77 条 |
| 验证样本 | 每类 2 条，共 154 条 |
| 检索候选 | Top-12 |
| 自进化规则 | 第一轮每类最多提升 1 条真实错误样本 |
| 冻结测试 | 每类均衡取 1 条，共 77 条；不参与更新 |

| 指标 | 基线 | 更新后 | 变化 |
|---|---:|---:|---:|
| 验证集候选召回 | 39.6% | 74.0% | +34.4pt |
| 验证集最终准确率 | 29.2% | 55.2% | +26.0pt |
| 冻结测试候选召回 | 35.1% | 59.7% | +24.6pt |
| 冻结测试最终准确率 | 27.3% | 46.8% | +19.5pt |
| 本机 CPU 端到端耗时 | 约 148ms/例 | 约 157ms/例 | 基本持平 |

这个结果说明收益首先来自正确类别更常进入 Top-K，随后 Laya 才能在较小且语义更相关的候选集合里做出更可靠的选择。它是“检索/经验层可行”的证据，不代表已经证明权重级训练也必然有效。

## 5. 版本与门禁：如何让系统真的可运营

每个 memory 或 checkpoint 都需要一个 manifest。manifest 不要求复杂，但至少要明确下列字段。

| 字段 | 作用 |
|---|---|
| model version | 当前 Laya checkpoint 或 adapter 版本 |
| memory version | 原型样本及向量索引的版本 |
| data snapshot | 数据来源、时间范围、哈希、脱敏状态 |
| update reason | 这一版为何产生，例如某类召回回归或新业务意图 |
| offline metrics | accuracy、macro-F1、Top-K recall、P50/P95 延迟 |
| risk checks | 关键类、越权、误执行、abstain 覆盖、校准检查 |
| release state | draft、offline-approved、shadow、canary、production、rolled-back |
| rollback target | 可一键恢复的上一稳定版本 |

发布门禁至少应覆盖质量、风险、系统和数据四类问题。

| 门禁类别 | 必须回答的问题 |
|---|---|
| 数据门禁 | 标签是否可信？是否存在测试泄漏、重复样本、PII 或权限问题？ |
| 质量门禁 | 总体准确率、关键类召回、长尾类表现是否优于或不低于当前稳定版？ |
| 风险门禁 | 是否扩大了误执行、越权、低置信错误自动化的风险？ |
| 系统门禁 | 延迟、CPU/GPU 内存、吞吐与异常率是否满足线上预算？ |
| 回归门禁 | 既有关键场景是否退化？是否已经准备好回滚？ |

## 6. 从经验层到模型层的升级路线

<whiteboard type="blank"></whiteboard>

### P0：静态基线

先固定任务定义、动作集合、数据切分和评测 protocol。没有可重复基线，后续“进化”无法判断是否真实有效。

### P1：原型记忆 RSI

只更新可信案例与类原型。适合当前阶段，目标是验证候选召回是否是主要瓶颈。Banking77 结果已经证明这一层值得继续做。

### P2：检索器 RSI

开始比较 Top-K、prototype 数、重排器、embedding adapter 和不同类别配额策略。所有选择必须只在验证集完成，完整测试集保持冻结。

### P3：模型级微调

在有 GPU、replay buffer 足够稳定后，才训练 Laya decision head 或 LoRA adapter。目标不是替代 P1，而是和 P1 做消融对照：到底是检索在创造收益，还是权重更新进一步提高了判别能力。

### P4：受控持续学习

引入延迟标注、人审采样、漂移检测和自动生成候选版本，但仍不允许自动上线。任何自动化只负责“提出候选版本”，不负责“批准自己上线”。

## 7. 建议的 JEV 落地顺序

### 第一周：把观测和边界搭起来

- 定义 JEV action schema：每个 action 的输入、权限、风险等级、成功判据和回滚方式。
- 为每次 Laya 决策记录 request、候选、choice、规则结果、执行结果与版本号。
- 先接入 abstain 与人工复核入口，而不是只追求自动执行率。

### 第二到三周：把 P1 变成可复验产品

- 用真实 JEV 场景构建首个 replay buffer，严格区分训练、验证、冻结测试与线上 holdout。
- 做 Top-K、原型数量、每类更新配额、多随机种子消融。
- 建立 memory manifest、离线报告和一键 rollback。

### 第四周以后：决定是否投入模型级训练

- 如果检索召回已高但 choice 仍常错，再投入 decision head/LoRA 微调。
- 如果检索仍是最大瓶颈，优先迭代 embedding、重排器和候选 schema，而不是过早训练大模型。
- 模型级版本必须在完整回归集、延迟预算和安全门禁全部通过后才进入小流量。

## 8. 当前结论

最有价值的不是“让 Laya 自己变强”，而是让 JEV 拥有一套能持续沉淀经验、验证收益、控制风险并可靠回滚的决策基础设施。当前最合理的路径是先把 P1 原型记忆 RSI 产品化，再用证据决定是否走向 P2/P3。
